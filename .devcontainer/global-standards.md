# 開発標準（全プロジェクト共通・Claude向け）

**位置づけ**: ソフトウェア開発のベストプラクティスを「あるべき姿」として定めた規範。
適用規模は個人開発（開発者1人 + AIエージェント、レビュアー・専任QA・複数環境なし）。
大規模開発向けのプラクティス（必須コードレビュー、複数環境昇格、カバレッジ目標、変更管理委員会など）は採用しない。
既存コードがこの標準を満たしていない場合、直すべきはコードであり、標準を現状に合わせて弱めない。
ギャップは各プロジェクトの CLAUDE.md にバックログとして明示する。
プロジェクト固有の仕様・制約はここに書かず、各リポジトリに置く。

## 1. 原則

- **シンプルさ優先**: 動く最小の実装を選ぶ。将来の想像上の要件のための抽象化はしない（YAGNI）
- **fail loudly**: 失敗は失敗として見える化する。静かに壊れるシステムを作らない
- **再現可能性**: 環境構築・実行・検証は手順化（またはコード化）され、いつでも再現できる
- **一つの事実源**: 同じ知識（スキーマ・定数・仕様）を複数箇所に複製しない

## 2. バージョン管理・変更管理

- **新機能の追加・既存の仕様変更は、実装に着手する前にPlanモードで計画
  （目的・スコープ・影響範囲・確認方法）を提示し、ユーザーの明示的なGoを得てから実装する**。
  バグ修正・1ファイル程度の軽微な修正・設定変更はこの限りではない（都度Planを挟まない）。
  「じゃあやってみて」等の会話的な同意だけで実装に入らないこと
  （2026-07-25、要件定義のステップが緩く実装に飛びつきがちという指摘を受けて追加）
- trunk-based（main直コミット）を基本とし、壊れる可能性が高い変更のみブランチを切る
- commitは1つの論理変更に対応させる。挙動を変える修正と変えないリファクタリングは分ける
- commitメッセージは「何を・なぜ」を書く（howはdiffが語る）
- 仕様に影響する変更は、仕様文書の更新を同じcommitに含める
- **pushは必ずユーザーに事前確認する**（push=本番デプロイとなる構成が多いため）

## 3. 品質保証

### 静的チェック
- 最低限、構文チェック（py_compile等）を変更のたびに通す。linterがあれば使う

### テスト
- **実行条件**: 外部サービス・秘密情報なしで実行でき、本番データを変更しない。1コマンドで全実行できる
- **決定性**: 乱数はseed固定。時刻・ネットワーク・実行順序に依存させない
- **レベル分け**（小規模では以下で十分）:
  1. ユニット: 純粋ロジック（パース・検品・変換）の境界値
  2. ゴールデン: テキスト/フォーマット出力を期待値ファイルと比較し、意図した変更のみdiffに現れるようにする
  3. スモーク: デプロイ後、最初の本番実行のログを確認する（後述の運用確認）
- **回帰**: 本番障害の実入力データはフィクスチャとしてテストに常設化する
- **CI**: テストはpush時に自動実行されるべき（手元実行だけに依存しない）

### 挙動不変の証明
- リファクタリング時は、変更前後の出力を採取して比較（ゴールデン比較）し、不変を機械的に確認する

## 4. エラー処理・回復性

- 例外を握りつぶさない（catch→printで継続しない）。処理を続ける明確な理由がある場合のみ捕捉し、理由を書く
- 「0件処理で正常終了」を許さない。バッチ/cronジョブは意図した仕事ができなかったら異常終了する
- 外部API失敗は分類して扱う: 一過性（5xx・タイムアウト）→限定回数のリトライ、恒久的（4xx）→即失敗
- ジョブは再実行安全（冪等）に設計する: 二重実行しても重複投稿・重複課金が起きない
- 部分失敗を状態に反映する: 「途中まで成功」を「全部成功」として記録しない

## 5. 運用・監視

- 定時実行ジョブの失敗は通知で気づける状態にする（CI失敗通知の受信確認を含む）
- デプロイ（push）後、最初の本番実行結果を確認するまでを変更作業の完了とする
- 障害は「事象・根本原因・対策」を記録し、仕様書または障害履歴に残す
- 消費型リソース（問題バンク・クレジット・容量）は残量が見える化されているべき

## 6. データ管理

- スキーマ（列定義・型）はコード上の一箇所で定義する
- 一意キーの採番は削除・並び替えで衝突しない方式にする（最大値+1、UUID等）
- 状態ファイル（DB・CSV）の削除・上書き前に、バックアップ（git履歴で足りるか）と影響を確認する
- 破壊的なスキーマ変更（列削除・意味変更）は、読み手側の互換対応を先に入れる

## 7. セキュリティ

- 秘密情報（APIキー・トークン）はコード・ログ・テストフィクスチャ・コミットに含めない。環境変数/Secrets経由で渡す
- 権限は必要最小限にする（トークンのスコープ、CIのpermissions）
- 依存パッケージは用途が明確なもののみ追加し、不要になったら削除する

## 8. ドキュメント

- **仕様（SPEC）**: システムの現行動作の正確な記述。変更のたびに更新し、常にコードと一致させる
- **標準（本書）**: あるべき姿の規範。現状追認で書き換えない
- **プロジェクトCLAUDE.md**: 固有の制約・quirks・標準とのギャップ（バックログ）
- 決定事項は理由とともに残す（「なぜピンク固定か」レベルの小さな決定も、覆すコストが高いものは書く）

## 9. 開発環境（Dev Container）

新規プロジェクトをDev Containerで構築する際は、以下を**都度確認を挟まず**初期セットアップに含める（参照実装: `versant-practice`の`.devcontainer/`一式）。

- **バインドマウント必須**: ホストフォルダを開いて「Reopen in Container」する既定の挙動を使う。
  「Clone Repository in Container Volume」等のコンテナ内蔵ストレージのみの構成は使わない。
  コンテナを削除するとコードごと失われるため（2026-07-26、english-quiz-botで実際に発生した状態から判明）
- **Claude Code CLI自体を必ずpostCreateCommandでインストールする**: ベースイメージ（Python等）には
  Claude Code CLIもNode.jsも入っていない。Node.js 20系 + `npm install -g @anthropic-ai/claude-code`
  をpostCreateCommandに含める（2026-07-26、versant-practiceで`claude`コマンド不在に気づき追加）。
  Microsoft系devcontainerベースイメージにはyarn用apt репоが未検証GPG鍵のまま入っており
  `apt update`を失敗させることがあるため、Node.jsセットアップ前に
  `/etc/apt/sources.list.d/yarn.list`を無効化しておくこと
- **Obsidian自動アーカイブ連携**: Windows側グローバル（`~/.claude/settings.json`のSessionEndフック→
  `vault_archive.py`→Obsidian vaultのdaily-notes）と同じ仕組みをコンテナ内にも用意する。
  具体的には、プロジェクトの`.devcontainer/`配下に`vault_archive.py`・`global-settings.json`
  （SessionEndフック定義、Linux用パス）を置き、`devcontainer.json`で
  Obsidian vaultのdaily-notesフォルダを追加バインドマウントし、
  postCreateCommandで`~/.claude/scripts/vault_archive.py`・`~/.claude/settings.json`へコピーする
  （2026-07-26追加。Obsidian vault構成自体の方針は別途[[obsidian_claude_scope]]で検討中のため、
  そちらの結論が変わったらこの節も合わせて見直す）
- postCreateCommandが長くなる場合は`.devcontainer/postCreate.sh`にまとめ、
  `devcontainer.json`からは`bash .devcontainer/postCreate.sh`の1行で呼ぶ（可読性のため）
- **新規プロジェクトのDev Container立ち上げ時は、既存の類似プロジェクト（コンテナ）に
  追加インストールされているツールを確認し、必要なら同様にpostCreate.shへ含める**。
  都度「入れて」と言われるのを待たず、新規プロジェクト作成の一連の作業として自動でやる。
  例: english-quiz-botには`gh`・`ffmpeg`・`fonts-liberation`が追加インストールされていた
  （2026-07-26、versant-practiceへ移植）。逆に、確認して実体が見当たらないもの
  （設定はあるが未インストール等の環境ドリフト）はそのまま移植せず、気づいた時点で報告する
